# Oathon — System Invariants

These properties MUST remain true across all supported implementations. Breaking an invariant is a release-blocking defect.

## INV-001 — Committed evidence immutability

Once an evidence event has been durably committed, its canonical evidence bytes MUST never be modified. Corrections MUST be represented as new events.

## INV-002 — Deterministic verification

Two conforming independent implementations given identical evidence artifacts MUST compute identical event hashes and signature-verification results.

## INV-003 — Single predecessor

Every non-genesis event MUST reference exactly one predecessor within the same segment. A genesis event MUST have prev_hash = null.

## INV-004 — Ordered writer sequence

Within a segment, sequence numbers MUST begin at zero and increase by exactly one.

## INV-005 — Writer isolation

A segment MUST belong to exactly one writer_id. Concurrent writers MUST NOT append independently to the same segment.

## INV-006 — Signed segment closure

Every closed segment MUST have an immutable segment-close record signed by a writer key that is certified, via a writer-authorization record, by an authorized organization signing key (CRYPTOGRAPHY.md §9b). *(Reworded per SC-2 resolution; ADR-012.)*

## INV-007 — Mutation detection

Any alteration to evidence fields covered by an event hash MUST cause verification failure. Any alteration to a signed object covered by its signature MUST cause signature verification failure.

## INV-008 — Idempotent ingestion

Replaying an identical accepted event or batch MUST NOT create a second logical event. Conflicting reuse of an existing identifier MUST be rejected.

## INV-009 — Tenant isolation

No supported API operation by Tenant A may read, mutate, revoke, anchor, report on, or enumerate Tenant B's private resources.

## INV-010 — No raw payload custody in v0.1

Oathon v0.1 servers MUST NOT ingest or persist customer prompts, model responses, tool payloads, document bodies, payment details, or arbitrary action payload bodies. Only approved metadata and cryptographic digests MAY be stored. `evaluation_metadata` limited to the mandate's declared `evaluable_fields` (MANDATE-014, EVENT-009) is approved metadata. *(Clarified per SC-1 resolution; ADR-011.)*

## INV-011 — Client private-key isolation

Organization private signing keys MUST NOT be transmitted to or generated by the Oathon server.

## INV-012 — Historical key preservation

A key rotation or revocation MUST NOT erase the public-key material required to verify historical signatures.

## INV-013 — Provenance separation

Reports MUST distinguish: OBSERVED, DECLARED, DERIVED, UNVERIFIED. A weaker provenance class MUST NOT silently be represented as a stronger class.

## INV-014 — Evidence gaps are visible

Broken, missing, unanchored, unverifiable, or incomplete ranges MUST be disclosed. They MUST NOT be silently omitted from a report.

## INV-015 — Anchoring honesty

RFC 3161 anchoring MAY establish that a specific digest existed by the TSA timestamp. It MUST NOT be represented as proof that:

- the original event was truthful
- no alternative history has ever existed
- the customer was uncompromised
- the TSA provides public transparency

## INV-016 — No negative claim from incomplete capture

A report MUST NOT claim "zero forbidden attempts," "no incidents," or equivalent absence claims unless the relevant capture coverage is sufficient to support that statement.

## INV-017 — Authority determinism

A within, outside, or ambiguous authority determination MUST be reproducible from the referenced mandate, the explicitly identified evidence set (AUTH-009), and the normative evaluation rules. *(Clarified per NEW-5 resolution.)*

## INV-018 — Network independence of local evidence

Temporary Oathon API unavailability MUST NOT corrupt an already-durable local chain.

## INV-019 — Failed persistence is never disguised

If evidence cannot be durably recorded under strict mode, the SDK MUST expose the failure. It MUST NOT pretend successful evidence capture.

## INV-020 — Report traceability

Every material report assertion MUST be traceable to machine-readable provenance metadata.

## INV-021 — No retroactive strengthening

Evidence collected under weaker capture, anchoring, or key-continuity conditions MUST NOT later be labeled as though stronger guarantees existed at collection time.

## INV-022 — Public protocol versioning

A semantic change to a frozen public v0.1 structure MUST NOT occur without a new compatible extension or protocol version.

## INV-023 — Per-writer segment continuity

The closed segments of one writer MUST form a chain via `segment_sequence` and `prev_segment_close_hash` (SEGMENT-010, CRYPTOGRAPHY.md §13). Verification MUST detect a missing or reordered closed segment within a writer's history. *(Added by NEW-3 resolution; ADR-014.)*

## Invariant verification

Each phase compliance matrix MUST identify which tests protect each applicable invariant.
